# 誤解ごとのスライド記載マップ

> 対象: [slides.md](slides.md) / [outline.md](outline.md)  
> 参照: `setting/editor_perspective.md`（構造・冗長・読者視点）, `setting.mdc`（pain_points / plot / serialization）  
> 確定した誤解ツリーを、**スライドに残すべき要素**に分解したメモ。

## スライド設計の原則（編集者視点）

各誤解スライドは次の3点だけを残す。それ以外は口頭か書籍・連載へ。

| 残す | 削る（スライドでは扱わない） |
|---|---|
| 信じがちな一文（親/子の見出し） | 解決策カタログ、チェックリスト全文 |
| なぜ崩れるか（1〜3行） | 同じ意味の言い換えの繰り返し |
| 1つの問い（takeaway） | 抽象論だけのスライド、根拠なき断定 |

共通フォーマット（子誤解）:

1. 見出し＝誤解名
2. `信じがち：…`（一文）
3. 崩れる理由（箇条書き）
4. （任意）図1枚
5. 問い1つ

共通フォーマット（親誤解セット）:

1. セクション扉（親の主張＋一行補足）
2. ストーリー1〜2枚（フィクション明示）
3. 子誤解の解説
4. DMM/実践の締めで「次に何を揃えるか」

## 地図（確定版）

- 速く出せば生産性が上がるという誤解
  - テストを削ればスピードが上がるという誤解
  - 動くものを早く出せば仕様は固まるという誤解
  - 「もっと早く」と押せばアウトプットは増えるという誤解
- 小手先指標による誤解
  - 測れる数字が正しい生産性という誤解
  - エンジニアだけが生産性を求められればよいという誤解
- 測れないから説明できないという誤解
  - 負債は測れないから語れないという誤解
  - 今動けばよくて、負債はあとで解消すれば良いという誤解
  - 売上に直結しない作業は優先度を下げてよいという誤解
- 人月の誤解
  - 人を増やせば速くなるの誤解
  - AIを入れれば速くなるの誤解
- 標準化の誤解
  - 同じ数字を全チームに当てはめれば比較も改善も進むという誤解
  - トップダウンで決めた指標を追えば現場の生産性は揃うという誤解

## セット1　速く出せば生産性が上がるという誤解

**対応**: 書籍第1章 / 連載第1回 / ペイン (2)(6)(8) ほか  
**セットの主張**: 短期は速く見える。中長期では崩れる。

### 親：速く出せば生産性が上がるという誤解

| 項目 | スライドに記すこと |
|---|---|
| 役割 | セクション扉＋連鎖の解説 |
| 信じがち | 速く出せば、生産性は上がる |
| 記す主張 | 短期の体感では「速い」。中長期では崩れる |
| 箇条書き | 設計軽視→手戻り / 品質省略→障害の利息 / 負債蓄積→変更が遅くなる / チーム疲弊→判断力低下 |
| 図 | 負のスパイラル（`chapter_1_negative_spiral.png`） |
| ストーリー | 「遅くないか？」／速さを追った先（仕様変更・QA削り・障害） |
| 締めで残す問い（セット共通） | 何のために・どの指標で・誰の何の判断に使うか |

### 子：テストを削ればスピードが上がるという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 検証時間を削れば、リリースは間に合う |
| 崩れる理由 | 削った時間は障害対応として利息で返る／内部品質は速さの敵ではない |
| 図 | Design Stamina Hypothesis |
| 問い | 今回のリリースで、削ってよい品質は合意済みか |
| 口頭へ | NISTの数値詳細、Fowler全文 |

### 子：動くものを早く出せば仕様は固まるという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 「変化に柔軟」＝計画不要。まず画面を出す |
| 崩れる理由 | 大枠のまま実装→変更のたび設計ごとやり直し／「変化に柔軟」と「計画不要」は別物 |
| 図 | 欠陥修正の相対コスト（NIST） |
| 問い | 動く前に決める最小セットは何か |
| 口頭へ | アジャイル論の長広舌 |

### 子：「もっと早く」と押せばアウトプットは増えるという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | プレッシャーをかければ、出せる量が増える |
| 崩れる理由 | 活動量は増えても判断力・改善意欲が削られる／疲弊→品質低下→残業のループ／SPACE：熱意・支援・フィードバック |
| 図 | なし（口頭でSPACE） |
| 問い | 何を止めて、何を急ぐのか |
| 口頭へ | バーンアウト統計の羅列 |

### セット1のDMM/実践スライド

- 速さの前に揃える三点（目的／指標／使い手）
- 決済基盤改修の翻訳ミス（計画の信頼性 →「とにかく早く」）

## セット2　小手先指標による誤解

**対応**: 書籍第2・4章 / 連載第2回 / ペイン (5)(9)(10)  
**セットの主張**: 測ること自体は誤りではない。壊れるのは「単一・評価直結・立場無視」。

### 親：小手先指標による誤解

| 項目 | スライドに記すこと |
|---|---|
| 役割 | セクション扉 |
| ストーリー | 「数字で示せ」／指標が目的化したチーム（水増し・簡単なタスク・細切れリリース） |
| 記さない | 指標リストの網羅、ゲーミングの全パターン |

### 子：測れる数字が正しい生産性という誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 測れる数字＝正しい生産性 |
| 崩れる理由 | 立場が違えば分子も分母も違う |
| 表 | レベル1仕事量／レベル2届いた施策／レベル3売上・KPI（広木） |
| 図 | Goodhart |
| 問い | この数字は、誰の・何の判断用か |

### 子：エンジニアだけが生産性を求められればよいという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 開発生産性はエンジニアだけの問題だ |
| 崩れる理由 | 事業側が見るのは計画の信頼性／Four Keys改善≠事業側の実感／内部健全性を事業満足の代理にしない |
| 図 | レイヤー別の意味（第6章） |
| 問い | 遅れの説明責任を、誰が・何の言葉で持つか |

### セット2のDMM/実践スライド

- ダッシュボードの前に聞く三問（何のため／誰が何に／評価直結させないか）
- 締めの一文: 数字をやめるのではなく、**使い方を変える**

## セット3　測れないから説明できないという誤解

**対応**: 書籍第3章 / 連載第3回 / ペイン (4)  
**セットの主張**: 測れないことと、説明できないことは分ける。

### 親：測れないから説明できないという誤解

| 項目 | スライドに記すこと |
|---|---|
| 役割 | セクション扉 |
| ストーリー | 「技術的負債があります」で詰まる（いくら・何週間・何が戻るか） |

### 子：負債は測れないから語れないという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 負債は測れないから、経営には語れない |
| 崩れる理由 | 活動量指標に出ないだけ／時間の流出・影響範囲・コスト換算なら語れる |
| 図 | Stripe週次時間内訳（基準線である旨をキャプションに） |
| 問い | いま失っている開発時間は、だいたい何か |

### 子：今動けばよくて、負債はあとで解消すれば良いという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 今出荷できればよい。利息はあとで払う |
| 崩れる理由 | 利息は次の変更から既に払っている／予兆・抑制・解消を混ぜると火消し専業になる |
| 図 | 技術的負債の対応フロー（予兆／抑制／解消） |
| 問い | 今スプリントで止める利息はどれか |

### 子：売上に直結しない作業は優先度を下げてよいという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 売上に直結しない作業は後回しでよい |
| 崩れる理由 | 売上直結しない≠価値がない／変更速度・障害コスト・開発スタミナに効く |
| 箇条（短く） | 四観点の定点観測（計画差分／変更・レビュー時間／障害／エンゲージメント）のうち2つから |
| 問い | やらない場合の、来四半期のコスト増は何か |

### セット3のDMM/実践スライド

- 三つの打ち手（四観点の2つ／返済工数の明示／コスト増の一枚）
- 一文: 可視化とコスト換算は、共通言語のための先行コスト

## セット4　人月の誤解

**対応**: 書籍第5章 / 連載第4回予定 / ペイン (3)(11)(12)(13)  
**セットの主張**: 「足りない」を人数に還元すると外れる。

### 親：人月の誤解

| 項目 | スライドに記すこと |
|---|---|
| 役割 | セクション扉 |
| ストーリー | 「現有リソースでどうにかして」「足りないのは本当に人数か」 |

### 子：人を増やせば速くなるの誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 遅れているなら、人を足せば速くなる |
| 崩れる理由 | 逼迫時の増員は調整・オンボーディングが先に膨らむ／『人月の神話』／足りないのは「何を作るか」を決める力かもしれない |
| 問い | ボトルネックは実装か、要件・優先順位・合意か |
| 口頭へ | 採用失敗エピソードの細部 |

### 子：AIを入れれば速くなるの誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | AIを入れれば、組織の生産性は上がる |
| 崩れる理由 | 個人実装が速くなってもボトルネックはレビュー・合意・待ちへ／AIは増幅器／既存プロセスに載せるだけでは頭打ちか混乱 |
| 図 | Faros AI Productivity Paradox |
| 問い | AI前提なら、何を止めて・何を人間が持つか |
| 口頭へ | 監視レベル表、チーム設計の詳細 |

### セット4のDMM/実践スライド

- 「人が足りない」ときの三軸（戦略／技術環境／組織能力）

## セット5　標準化の誤解

**対応**: 書籍第7章 / 連載第6回予定 / ペイン (5)(9)  
**セットの主張**: 全社で同じ数字を追わせること ≠ 生産性が揃うこと

### 親：標準化の誤解

| 項目 | スライドに記すこと |
|---|---|
| 役割 | セクション扉 |
| ストーリー | 上が決めた指標を全員が追う／文脈差を無視した比較／考える余白が消える |

### 子：同じ数字を全チームに当てはめれば比較も改善も進むという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 同じ数字なら、比較も改善も進む |
| 崩れる理由 | 比較のための統一は文脈差を消しゲームを生む／DORAとSPACEは対と束。片方を全社公式にしない |
| 図 | DORAとSPACE |
| 問い | この数字は比較用か、学習用か |

### 子：トップダウンで決めた指標を追えば現場の生産性は揃うという誤解

| 項目 | スライドに記すこと |
|---|---|
| 信じがち | 上が決めた指標を追えば、現場は揃う |
| 崩れる理由 | 追従は「数値を追う組織」を作り主語を奪う／揃えるべきは指標のコピーではない／目的・使い方・次の打ち手の合意が先 |
| 問い | チームが「止められる指標」「変えられる指標」を持っているか |

### セット5のDMM/実践スライド

- 標準化の先：自分たちで指標を設計し、チームの生産性を考える側へ
- 一文: 重圧は消えない。翻訳しながら判断できるようになる

## 導入・締めに記すこと

### 導入

| スライド | 記すこと |
|---|---|
| タイトル | 書籍名トーン／連載名・話者 |

### 締め

| スライド | 記すこと |
|---|---|
| 五つの誤解を一文で | 速さ／測れる数字／負債の物差し／人月・AI／全社統一 |
| 明日15分の三問 | 何のため／どの指標／誰の何のため |
| Takeaways | 主張と問いを残す。カタログは口頭へ。指標は対話のきっかけ |
| 続きはこちら | 書籍・連載の導線 |

### 予備（本編外）

本編で触れない／時間が余ったときだけ:

- 無駄な資産の蓄積
- 生産性パラドックス
- 認知的負債

## 編集者視点チェック（このマップ自体）

- **主張は明確か**: 各セットは「〜という誤解」で入口が一意
- **論理の飛躍**: 子は親の主張の分解であり、別論に逸れない
- **冗長**: 同じ「正しさ」を子と親で二重に言わない（親＝フレーム、子＝具体）
- **読者が離脱しそうな箇所**: 図付きスライドの数値解説を長くしない／解決カタログを並べない
- **スライド1枚1仕事**: 信じがち → 崩れる理由 → 問い
