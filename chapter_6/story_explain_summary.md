# 第6章　エンジニアだけが開発生産性を求められる重圧 — ストーリー／解説要約

> 参照: `chapter_6.md` / `plot.md` / `pain_points.md` / `setting/reference/merged_references.md`

## ストーリー要約（重圧・ペインベース）

- 成果が出ても「経営層にどう説明するか」が重圧になり、エンジニア指標だけでは伝わらない不安が残る
- 事業側が見るのは Four Keys の改善そのものではなく、**計画を信じて立てられるか**という信頼性
- 技術用語をビジネス用語へ翻訳し、開発生産性ツリーで「お金と時間がどこに使われているか」を共通言語化する
- 評価の軸をビジネスインパクト・持続可能性・効率性へ広げ、「エンジニアだけの問題」から組織の取り組みへ移る

## 解説パート要約（文献リンク付き）

### 6-1 エンジニア視点とビジネス視点の融合

- 重圧の背景は、**測っているものが層ごとに違い、共有されないまま評価だけが求められる構造**
- 開発側：リードタイム・デプロイ頻度・失敗率・MTTR（[DORA / Four Keys](https://dora.dev/guides/dora-metrics/)）
- 事業側：計画信頼性・予測可能性（欲しいタイミングで届くか）
- 本質は約束の信頼性。内部健全性の改善がそのまま事業満足になるとは限らない

### 6-2 共に創る「共通の価値基準」

- 技術的負債 → 開発効率低下リスク、リファクタ → 将来への投資、など翻訳の型をつくる
- 「人が足りない」とき足りないのは人数ではなく、優先順位を決める力かもしれない
- 個人と組織のギャップ（AIで個人が速くても組織成果に出ない）は歴史的生産性パラドックスと同型（第3・5・7章および NBER 系の議論）
- 知覚とワークフローの併用（[DevEx](https://queue.acm.org/detail.cfm?id=3595878)）、時間ベース計測の一例として [DAT (Meta)](https://arxiv.org/pdf/2503.10977)
- ROI・儲かるかへの答え方の補助線（[石垣「『開発生産性を上げる改善』って儲かるの？」](https://speakerdeck.com/i35_267/is-development-productivity-profitable)）

### 6-3 開発生産性を評価制度に組み込む

- 評価直結の単一指標はゲーミングを招く。軸を複数にし、学習と改善に使う
- AI時代は個人のタスク完了速度より、複雑なシステムをどう統制するかが分ける（McKinsey 系の整理）
- [DORA 2025](https://dora.dev/research/2025/dora-report/)：AIは仕事システムの変革であり、ツール導入単体ではない
